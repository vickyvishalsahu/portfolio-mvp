How your Gmail becomes a portfolio

The app gets read-only access to your Gmail, pulls broker emails into a local SQLite table, then asks an LLM to turn each email into buy/sell/dividend rows. The dashboard is built from those rows. You trigger each step yourself from the Sync page.

The three pieces

Once

Connect Gmail

Standard Google sign-in (OAuth) asking for the read-only Gmail scope. The app can't send, delete or modify mail.

Google hands back a long-lived refresh token, which is saved in the settings table so you don't have to log in again.

Step 1

Fetch

Runs a Gmail search roughly like:

category:purchases OR from:broker-domain …

  • Broker domains come from the brokers you picked plus a built-in list.
  • Each match is downloaded, and sender, subject, date and body (first 10k chars) are stored in raw_emails.
  • Already-seen emails are skipped, so re-running is safe.
Step 2

Parse

Goes through every email not yet parsed, cheapest check first:

  • Quick filter: is it from a known broker, or does the subject say "order", "dividend", "SIP" and so on? If not, skip.
  • Learned skips: drops senders/subjects it has learned are newsletters or other noise.
  • LLM: otherwise sends the email to the AI model, which returns structured trades (ticker, qty, price, currency, date, broker).

Trades land in transactions. Failures are kept so you can retry them.

Where the "instructions" actually live

Choosing which emails to grab doesn't use a prompt or any AI. It's a normal Gmail search, the same kind you'd type in the Gmail search bar. Groq only gets involved later, once the emails are already on your machine. (Groq is the fast-inference service, not xAI's Grok.)

Fetch: no LLM

The Gmail search

The Fetch button sends this to the Gmail API (built in buildSearchQuery):

category:purchases OR (
  from:zerodha.com OR from:camsonline.com
  OR from:angelone.in OR from:scalable.capital
  OR from:binance.com OR from:coinbase.com
  OR from:camsmail.com OR from:groww.in
  OR from:angelbroking.com OR from:mail.binance.com
  OR from:mail.coinbase.com )

The first six domains are the brokers you picked in setup. The rest come from the app's built-in broker list, which gets added because the UI always runs a full-history fetch. category:purchases is Gmail's own "Purchases" tab, so it also pulls in Amazon orders, receipts and so on. The parse step weeds those out.

Parse: Groq + prompt

The LLM call

AI_PROVIDER=groq, model llama-3.1-8b-instant, JSON mode. Each email gets a system prompt plus the email itself:

system: You are a financial transaction parser.
  Extract investment transaction data from broker
  confirmation emails. Return ONLY valid JSON …
  + rules: stock vs etf vs mf vs crypto,
    ticker must be a real symbol/ISIN or null,
    per-unit price, unparseable=true for marketing

user: Parse this broker email:
  From: …  Subject: …  Body: …

The full prompt is in domains/transaction-parsing/providers/constants/prompts.ts.

Fixed (staged): the quick filter's broker list was empty. The filter now trusts the same domains the fetch searches (your selected institutions plus the built-in broker list). In a test copy of your data, dropped CAMS statements now reach the LLM.
New blocker: Groq no longer serves llama-3.1-8b-instant. Every parse call fails with model_not_found. 1,609 emails in your DB have already failed this way. Models your key can use include openai/gpt-oss-20b, openai/gpt-oss-120b and qwen/qwen3.8-27b.
Original finding: The parse step's first check is meant to wave through anything from a known broker domain, but BROKER_CATALOG in domains/shared/constants.ts is []. In practice only the subject-keyword check works, so a broker email whose subject lacks words like "order", "trade" or "dividend" (say, a contract note titled "Your statement for 05-Nov") is skipped and never reaches Groq. I haven't fixed this. The other list, KNOWN_BROKERS, already has these domains.

Worth knowing

It's not Claude doing the parsing. The project docs say "Claude parsing", but the code uses Groq (Llama 3.1 8B) or Google Gemini, picked by AI_PROVIDER in .env.local. Either the docs or the code is out of date.
Your email bodies leave your machine at one point. Everything is stored locally except during Parse, when the full text of each candidate email goes to the LLM provider. Emails the quick filter or learned skips reject are never sent.
It quietly learns what to ignore. After a parse run, if the LLM rejected 3+ emails from the same sender, a second small LLM call pulls out subject keywords, so similar emails get skipped next time without an LLM call.
